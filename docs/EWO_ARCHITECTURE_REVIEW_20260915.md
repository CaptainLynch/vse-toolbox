# EWO 架构方案评审 — 2026-09-15

对象：docs/EWO_MAPPING_EVIDENCE_ARCHITECTURE_20260915.md。结论：方向认可，当前版本不通过实施准备评审。主控基于当前代码与已读取附件进行自审，并非独立第三方审计。本轮无产品变更、无生产请求。

## P1-1：内部Item ID被直接定义为长期绑定键，缺少版本连续性合同

位置：原方案34、53行。410个唯一ID且is_current=1只证明本次结果唯一，不证明修订后仍为同一个ID。原方案虽记录generation/modified_on，却没有定义ID变化时是同一业务对象的新版本、另一个对象还是绑定失效。当前代码record_identity仍用业务编号，不能仅切换单记录绑定而保留发现、候选、集合指纹等旧规则。

风险：升级后绑定无法命中或跟随错误版本；4条空编号记录进入分析却不能在现有发现/执行链中保持一致身份。

修订要求：区分sourceItemId（观察到的记录/版本ID）、entityKey（只有验证修订连续性后才能建立）、businessNumber（关联/展示）；首期无连续性证据时将绑定明确为固定Item ID，失效则暂停并重新确认，禁止自动跟随同号。提供EWO专属identity contract版本，发现/预览/执行/指纹一致使用；不要修改其他来源的全局身份优先级。

验收：同号不同ID、同ID内容变更、空编号、非当前版本、修订替换及旧绑定升级；不静默接续、不丢分析行、不改变其他报表身份。

## P1-2：安全关联不等于可授权写回；缺乏快照一致性证明

位置：原方案38、67、69行。方案允许非空唯一编号拼接增强字段，并写“若发现列表变更则阻止”，但没有规定如何发现。导出无内部ID/版本，列表与导出先后执行；同号、同行数、同状态不能排除中间待签人员变化，也不能证明关联的是同一版本。即使导出前后列表modified_on不变，也未证明工作流待签变化一定更新该字段。

修订要求：首期官方增强限只读展示和分析，不进入自动项目字段写回；基础列表原有经验证字段可继续按明确策略运行。若未来开放增强写回，必须另定字段级一致性/时效合同并验证工作流版本证据。基础与增强各有snapshotId、输入范围签名、获取时间；明确matched/unmatched/ambiguous及available/source_empty/unavailable/invalid，缺失与失败都不构造清空候选。

验收：导出期间变更、同号不同版本、人数变化而主记录时间不变、部分增强缺失、增强过期；全部不得自动覆盖备注。只读分析允许非原子快照，但必须展示时间和范围。

## P1-3：导出生成存在结果未知窗口，单任务互斥不足以避免重复生成

位置：原方案61行。服务端生成成功、客户端尚未收到file引用时超时或退出，无法区分未执行与已执行。“按文件引用恢复”只覆盖引用已经收到且保存的情况。

修订要求：先定持久任务状态机：queued→generating→generated→downloading→parsed/failed，另设generation_unknown。生成前保存operation ID、输入ID集合摘要、身份/来源范围和attempt；生成成功后持久保存允许的文件引用，下载token只驻内存。进程恢复时generating一律转unknown，不自动重新调用生成方法；有文件引用则重新获取token恢复下载。用户主动重试unknown需明确可能重复生成；无证据不声称客户端幂等能保证服务端恰好一次。

验收：发送前/发送后/响应后持久化前/下载中分别崩溃，token过期，任务重复触发，租约到期。未知生成不自动重试，不复用跨账号文件引用。

## P1-4：能力和身份迁移路径不完整，阶段顺序可能先改变行为后建立合同

位置：原方案69、73–75行。A先改绑定语义，C才规范身份；同时要求旧行为兼容和新集合固定字段所有权，没有定义旧配置如何执行。当前签名白名单不包括新模式/合同版本/增强要求；仅写入matchRule可能被丢弃或拒绝。数据库观测、稳定性门禁和前端都依赖既有aggregate/外部键。

修订要求：先完成版本化合同及兼容适配，再开放UI保存新模式。legacy保持旧签名和读取规则；v2使用独立显式字段及确定性签名，不能放宽所有未知键。迁移预览列出来源、模式、身份及可写字段变化，转换后旧授权证据失效，重新取证才启用。无法安全转换的配置标为需处理，不能静默停止而无提示，也不能自动沿用授权。回滚旧客户端禁止修改v2绑定。

验收：旧配置回读、转换失败、转换中并发编辑、证据失效、旧客户端写v2被拒绝、回滚不覆盖新审计；升级前后的字段所有权差异可见。

## P2-5：字段映射和状态统计缺少逐值验证及明确分母

位置：原方案13、字段合同及单记录与集合模式。非空计数尚不能证明_rsp_name/_required_date与导出列逐值一致；CANCEL/OPEN只说单独显示，没有定义完成率分母、未完成数和超期统计。方案也未明确CLOZ日期表头别名与CLOSE状态的关系、日期空值/时区/格式错误处理。

修订要求：对406个唯一非空编号做本地逐值比对，仅输出一致/差异数量及脱敏模式；待签人员不得以负责人替代。推荐原始总数=410保留；取消单列，不算成功完成；有效完成率是否排除取消作为显式业务政策，禁止直接复用PAA规则。单独报告无业务编号4条与增强未关联4条，避免总数在视图间无解释地变为406。

验收：日期格式和时区边界、CLOZ表头、OPEN/CANCEL/未知状态、空日期、多个未签人，以及统计总数守恒。业务分母需产品确认后落实。

## 建议调整后的首期

1. 先完成EWO v2身份、能力、签名、字段可用状态和legacy兼容设计，明确固定版本绑定与迁移边界。
2. 修正UI的集合/单记录语义；保留基础列表字段同步，不承诺尚不存在的待签自动更新。
3. 新增持久官方导出任务与只读增强解析，验证111列和错误dimension、410/406/4计数、安全关联与恢复状态机。
4. 增强字段自动写回另设后续门禁；PAA/NCR扩展继续后置。

无需重复采集同一HAR即可推进上述只读增强设计和本地字段对照。若要求跨修订自动跟随或待签字段自动写回，才需要有针对性的修订/审批变化证据；更多相同静态HAR无法证明这些合同。
