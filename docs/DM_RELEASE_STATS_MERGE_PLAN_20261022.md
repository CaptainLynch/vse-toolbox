## 一、结论先说

1. **改动只发生在 D5 的数据解析与展示这一条链路上**，不做跨交付物的通用维度。`_dimensions_from_tdc` 只服务 `tdc_data_model`；D5 与 SOR 共用阶段图分支的风险已用"专属函数 + 提前返回"隔离，并有回归测试守着。
2. **不能用零件号把两份报表 join**：两份导出零件交集只有 3 个（均为通用件），架构件与项目件基本是互不相交的零件集合。合并只能是「并集 + 来源标注」。
3. **不能用「报表里填的项目/车型」当唯一归属**：架构件报表 94 个流程实例里，34 个的 SOR 号指向 `F710S`、2 个指向 `F620S`；反过来项目件报表里也有实例的 SOR 指向 `F710S`。报表车型 ≠ 数据真实服务车型。
4. **统计粒度必须用「流程实例（实例号）」**：一个实例最多含 22 行零件，按行计会严重重复计数；状态是实例级属性（实测每实例内状态唯一）。
5. **`已废弃` 在交付物快照里通常不存在**：归档连接器在写入表单快照前就用 `exclude_tdc_scope_rows` 剔除了 `已废弃`/`已撤回`，丢弃数走 `tdc_scope_exclusion` 诊断披露。归集模块仍按三态实现（直接导入整份导出时三态齐全），但 D5 看板日常只有 `已完成`/`审批中` 两态。

## 二、D5 现状与要改的那一个点

D5 交付物的表单定义里，维度映射是：

```
dimension_labels = {"section": "部门", "model": "发布属性", "stage": "项目 / 车型"}
```

即「项目/车型」列被当作 `stage` 维度，看板按它分组筛选（源码注释也写明"阶段图按观察到的项目/车型值聚合"）。所以现在 F620S 的 D5 视图里只会看到 `F620S` 这一群，`Ar-L` / `Ar-L+` 各自独立成群，项目件与架构件被割裂。

**要改的就是这一个点**：在 D5 的维度提取里，把「项目/车型」拆成「归集车型 + 数据来源」，让同一个车型下同时出现项目件与架构件两行状态。

## 四、归集规则

```
取一条流程实例
├─ EWO/SOR号 能解析出车型码？  → 归该车型，归属方式 = SOR号证据
├─ 否则 流水单号 有车型前缀？  → 归该车型，归属方式 = 流水单号证据
└─ 都没有                      → 归「平台池-<平台>」，归属方式 = 平台池（待归属）
```

- **证据归属 ≠ 适用关系证明**：SOR 号只能证明"这次发布针对该车型的需求"，不能证明"该件不服务其他车型"。所以保留 `归属方式` 字段，允许事后修正。
- **实例级统一**：同一实例内多行证据不一致时（有的行有 SOR 号、有的行是 TBD），按"证据优先于平台池 → 证据之间按行数多数 → 平票按 SOR 号 > 流水单号 > 车型代号最小"合成一份，再写回该实例所有行。这样阶段图（行级聚合）与实例汇总不会互相矛盾。
- **跨车型守卫**：同一实例的 `项目/车型` 原值不一致时不做归并，保留行级结果（实测 1037 行 0 例外）。
- **平台池不进车型合计**：无证据的 58 个实例单列，避免把 `F710S` 的架构数据静默算进 `F620S`。
- **一个架构实例只归一个车型**（SOR 号优先，其次流水单号）。若一个实例的零件确实分属不同车型，属于流程拆分需求，回到 TDC 层解决，不在统计层硬凑。
