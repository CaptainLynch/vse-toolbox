## 〇、两条必须记住的反面结论

### 1. SOR 号不能作归属证据

`EWO/SOR号` 里的 `SGMW-<车型>-SOR####` **不是**"这单服务哪个车型"的证据。它是零件的
定点/SOR 文档编号，属于**零件**，不属于**数模审批单**。

批次实测反证：项目件报表 228 个实例中 35 个带车型 SOR 号，其中 **3 个的发布车型是
`F620S`，SOR 号却写着 `F710S`**。若 SOR 是发布归属，这个数字应当是 0。

早期版本曾把 SOR 设为最高优先级证据，结果是架构件 94 单里 **34 单被错误归到车型**
（F710S 34 / F620S 2），并据此写出过"平台池 58 单"的结论——那 34 单是假信号撑起来的。
该实现已整体删除，`dimension_fields()` 现在**没有** EWO/流水单号入参，测试里锁死这一点。

同理，`流水单号` 前缀（`F710S-3D-0248`）只是历史编号习惯，2026 年那批已变成
`3D-0000xxxx` 不再带车型，因此也**不作归属证据**。

### 2. 项目派单台账不存在，不能拿 TDC 按车型查询冒充

用户 2026-10-23 确认：台账不存在，"这个就是 TDC 的查询结果"。

这在结构上就堵死了：按车型查询（`projectModel=F620S`）返回的行 `项目/车型` 只能是
`F620S`，**不会包含任何 `Ar-` 行**；实测两份导出交集为空（报表 36 无一条 `Ar-` 行，
报表 37 无一条 `F620S` 行）。所以"用车型查询结果当台账"等于台账里永远没有架构件单，
(a) 会退化成空集。

因此代码里不保留任何台账入参。若将来出现**独立于 TDC** 的派单台账，须以显式参数
重新引入、先补口径评审与回归测试——**不得**改用 SOR 号或流水单号顶替。

## 一、结论先说

1. **默认两类数据分开统计**：项目件按车型，架构件按架构平台，同页并列，互不并入。
2. **可选：车型兼顾架构件（方案 B，已实施）**。用户在车型下**显式指定**架构件单号，
   确认（已匹配）后并入该车型合计；同时保留"仅项目件"数字作对照。
   声明是人工口径，记录操作者/依据/时间，可撤销、可追溯。
3. **报表内没有可靠字段能把架构件单关联到车型**，可用的推断（SOR 号、流水单号前缀）
   都已被数据和业务澄清否掉；台账也不存在。所以**自动归集不做**，只接受人工声明。
4. **统计粒度用流程实例（`实例号`）**：一个实例最多含 22 行零件，按行计会严重重复计数；
   状态是实例级属性（实测每实例内状态唯一）。注意：阶段图是**行级**计数，
   `vehicleArchLinks` 汇总与工作簿是**实例级**，两者单位不同，已在载荷里分别命名。
5. **`已废弃` 在交付物快照里通常不存在**：归档连接器写入前用 `exclude_tdc_scope_rows`
   剔除 `已废弃`/`已撤回`，丢弃数走 `tdc_scope_exclusion` 诊断。分组模块仍按三态实现，
   但 D5 看板日常只有两态。

## 二、口径

| 数据来源 | 判定 | 分组键 | 归属方式 | 是否进车型合计 |
| --- | --- | --- | --- | --- |
| 项目件 | `项目/车型` 是车型代号（`F620S`） | 车型 | 自身车型 | ✅ |
| 架构件（无声明） | `项目/车型` 是平台代号（`Ar-` 开头） | 架构平台 | 平台单列 | ❌ |
| 架构件（已声明且已匹配） | 用户显式指定单号 ↔ 车型 | 该车型下的「关联架构件」 | 人工声明 | ✅（方案 B） |

**方案 B 的车型合计** = 项目件 + 已确认关联的架构件；"仅项目件"数字同时保留。
同一架构单被多个车型声明时，各车型视图分别计入（关联覆盖），
跨车型合计按单号去重（`linkedInstanceCount`），**不得把各车型数字直接相加**。

**失配四态**（必须分开披露，不能静默少算）：

| 状态 | 含义 | 是否计入 |
| --- | --- | --- |
| 已匹配 | 单号存在，且 `项目/车型` 确为平台 | ✅ |
| 来源不符 | 单号存在但是项目件（声明写错） | ❌ |
| 快照缺失 | 清单里有，本次快照查不到 | ❌，单列披露 |
| 键冲突 | 同一单号匹配到多个实例 | ❌，阻断该单 |

脏值归一：`620S` → `F620S`；`F620S产品项目` → `F620S`（保留原始值列便于追溯）。

## 四、统计口径

| 项 | 规则 |
| --- | --- |
| 主口径粒度 | 流程实例（`实例号`）；零件行只作明细下钻 |
| 状态 | `已完成` / `审批中` / `已废弃` 三态，实例级取值 |
| 完成率 | **已完成 ÷（已完成 + 审批中）**；`已废弃` 单列，不进分母 |
| 去重 | 实例级按 `实例号`；零件级按 `(实例号, 零件号)` |
| 车型合计（方案 B） | 项目件 + 已确认关联的架构件；"仅项目件"数字保留作对照 |
| 跨车型合计 | 按单号去重（`linkedInstanceCount`），禁止把车型数字相加 |
| 人工声明 | 记录 车型/单号/依据/操作者/记录时间/生效期/revision；撤销保留历史 |

## 八、专家顾问意见与裁决

### 第一次（口径与归集模型，run `e634b47c…`, sol-xhigh）

结论：保守归集、平台池不进默认合计、实例级口径。**前提是我给错的 SOR 归属假设**，因此
"归集模型"一项的结论已随 SOR 一起作废；口径与粒度两项仍然有效。

### 第二次（实施前架构评审，run `1812448a…`, sol-xhigh）

结论：落库只写 `dimensions_json`、暂缓索引列、D5 单设聚合入口、保留原 `stage`。**三项均采纳并已落地**，
与 SOR 无关，继续有效。并核实出 `已废弃` 被上游剔除这一口径事实。

### 第三次（范围方案，run `cbd11ac9…`, astra-medium）

问的是"以车型为基础 + 补充几个流水单号"是否可行。结论：**A 不成立**（TDC 无单号查询参数，
且车型过滤会结构性排除架构件）、保留 C 叠加 D、必须留口径与成员版本、未归集规模必须显式披露。
顾问同时纠正我把"范围法一定更慢"说强了——这一点我没有证据。

### 第四次（手工指定单号，run `b039a80…`, astra-medium）

问的是"车型兼顾手工指定架构件单"能否实施。三项全部采纳：
① 口径选 A（对照）、B 有条件——**用户随后选了 B**，故按"保留项目件数字 + 合计口径"实施；
② 独立关联表、不复用 `watchlist`（后者是落库范围，混用会绑死同步与统计）；
③ 同一单多车型各计一次，全局按单去重，并落成一条可验证断言。
顾问另指出：关联表只能记录声明，补不了同步遗漏——这正是"快照缺失"失配态的由来。
