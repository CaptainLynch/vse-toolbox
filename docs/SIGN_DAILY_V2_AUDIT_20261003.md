## 1. 开工前唯一待确认项：host.context 开放了什么（规格 §12、R1、R2）

| 项 | 结论 | 证据 |
| --- | --- | --- |
| 自有存储、结构迁移（R2） | **可用，不改宿主** | `host/registry.py` `PluginHost.migrate()`、`table_prefix`；前缀是 `p_sign_daily_`（`core/repos/plugin_schema.py:34`），不是规格写的 `signing_report_`。v1 已用它建了 `config`、`daily_summary` 两张表 |
| 触发 TDC 抓取（R1） | **可用，不改宿主** | `ctx.services` 就是整个 `app.extensions`（`web/app.py:6173`）；v1 已经调 `scheduled_archive_admin.sync_now("tdc_data_model")`（`backend.py:371`） |
| 查询抓取进度（R1） | **没有现成的，可组合实现** | `sync_now` 在 HTTP 请求里同步跑完整个抓取，页面没有进度。`crawl_task_runner.submit_task(worker_fn=…)` 和 `get_task()` 也在 `app.extensions` 里，插件可把 `sync_now` 包进后台任务再轮询，不用改宿主 |
| 与自动同步共用抓取锁（R3） | **锁已存在** | `ArchiveSyncRunner` 的租约（`lease_seconds=900`）。手动和调度并发时返回 `lease_busy`。v1 把它当失败提示「稍后重试」，规格要求复用进行中的任务，要改成等待并轮询 |

**风险**：`app.extensions` 不是声明过的插件契约，键名一改插件就失效（和 R5 同类）。
建议宿主在 `HostContext` 文档和 `tests/test_plugin_host.py` 里把
`scheduled_archive_admin`、`crawl_task_runner` 登记为插件可用的服务名。改动小，但要单独评审。

**插件 id 不改名**：沿用 `sign-daily`。改成 `signing_report` 会让 v1 已存的配置表和日汇总表成为孤表。

与规格的两处有意偏离：
- 花名册本地层按「规范化姓名」做主键，不是「姓名 + 科室」。同名不同科室在导入时就按冲突拦下（规格的默认行为），所以生效花名册里不会出现同名两科室。
- S19「同步进行中修改不打断当前这一次」只对启用和间隔成立。改筛选条件或更新方式会让进行中那次的结果不发布（宿主既有的 `sync_config_revision` 保护，避免新旧设置混用），编辑区里写明了这一点。

## 11. 规格 10-04 修订（F620S 在途样例）的落地

规格在 10-04 用 F620S 的 19 份在途单修订了在途相关规则。代码按修订重写，`rules.py` 的改动如下：

| 规格 | 改动 |
| --- | --- |
| A10 | 当前待办 = 待审批人员里的每一项（原来是「未签且在待审批人员里」）。带「(未签)」但不在待审批人员里的人叫「未签但非当前待办」，不计欠账，明细表末尾写「另 n 人未签、非当前待办」 |
| A12 | 待审批人在多个节点都未签，只算流转顺序（设计工程师、主任工程师、会签、专家/经理、首席/总监）上最靠前的节点；最靠前的是会签时，他所在的每个会签列都算 |
| A13 | 不在任何角色列的待审批人：已签的设计工程师记「退回修改」进图3 设计工程师组；其余是加签人，在册取花名册科室，未在册取他在本次数据里出现最多的会签列（次数相同取列顺序靠前的），从没出现过的归「加签（区域未知）」，固定排在图1 最后。会签列还有未签时算会签阶段，否则挂在第一个仍有未签的审批节点下 |
| T1–T6 | 阶段改为会签中、审批中、退回修改、待提交、待锁定；取消「加签中」和「会签中·含加签」。待审批人员为空但还有未签时按 T2 判阶段，明细表该行标「无待审批人」 |
| P3/P6/P7/P10 | 待审批人员支持半角逗号，同一人可重复，仍按「人 + 单」算 1 单；已知在途状态加上「审批中」；会签人次按名字出现次数计、不去重，并校验「角色列人次 + 加签人数 = 应签人数」，不等记 `requiredCountDiffer` 异常；流水单号一律整串处理 |
| A5/A9 | 历史科室加上「视觉工程科」（内饰科、外饰科的旧名），申请人在册时按花名册科室拆分，不在册时显示「视觉工程科（未拆分）」并提示 |

这次解读规格时选了两处，规格没写死：
- 加签人在审批阶段挂在「主任工程师、专家/经理、首席/总监」里第一个仍有未签的节点，不挂设计工程师（否则 T5「当前待办只有设计工程师本人」会和加签人冲突）；这三个节点都没有未签时挂主任工程师。
- 加签人在会签阶段出现次数只统计会签列，按「单 + 列 + 人」各算一次，范围是本次生成用到的全部单（含已完成）。

没动的：规格留给用户拍板的「后蒙皮上组件、后蒙皮下组件」要不要算确定命中（现在落在疑似），代码保持原规则。
