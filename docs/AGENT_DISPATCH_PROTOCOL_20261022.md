# Agent 派发与等待协议（2026-10-22 定案）

本文件把 2026-10-21/22 长会话审计（会话 `session-12887aa2`，19 轮、458 次工具调用、
422 次模型调用、墙钟 24,487s ≈ 6.8h）的实测结论固化为可执行规则，并记录专家顾问
复核的裁决。实现见 `tools/agents/dispatch_wait_protocol.py`，测试见
`tests/test_dispatch_wait_protocol.py`。

## 1. 实测结论（先看数字，别猜）

| 项目 | 实测值 | 说明 |
| --- | --- | --- |
| 会话墙钟 | 24,487s | 19 轮 |
| **子代理串行关键路径** | **19,296s（79%）** | 35 次派发，单次 259–1,423s，中位约 420s，全部串行 |
| pwsh 轮询等待 | 10,385s（42%） | 48 次固定 300s 轮询，其中 27 次撞满上限（8,112s） |
| 用户回答等待 | 2,332s（10%） | 1 次提问，与子代理运行完全串行 |
| 全量 pytest | 12 次，单次 345–379s | 迭代期反复全量 |
| 模型步时延 | 422 步，中位 9.6s | 与上下文长度几乎无关（见下） |
| 单步最大输入 | 520,716 token | 治理硬闸 200k，实际超 2.6 倍；累计输入 3.15M token |

两条被数据推翻的直觉：

1. **顾问不是瓶颈。** 4 次 live 咨询合计 471s（1.9%），全部后台启动。不要为了省时间砍顾问。
2. **上下文膨胀不是墙钟主因。** 按输入 token 分档统计模型步时延：`<50k` 中位 9.5s（n=415），
   `>350k` 中位 15.4s（n=5）。上下文治理关乎**成本与质量**（3.15M 输入 token），
   不关乎墙钟；墙钟只能靠缩短子代理关键路径。
3. **轮询时间约等于子代理真实运行时间**，不是"额外浪费"；它的真实代价是 48 次多余模型往返
   与上下文增长。真正的浪费是**串行**与**迭代期反复全量测试**。

## 2. 定案规则

### 2.1 等待：标记文件 + 多路等待器（顾问：决定 1 = adopted）

- 每个子代理必须在结束时**原子写入** `<repo>/.agent/status/<task_id>.<role>.json`
  （先写临时文件再 rename）：`status`（`running|done|failed|blocked`）、`changed_files`、
  `commit`（可选）、`started_at`、`finished_at`、`progress_at`。
  里程碑处刷新 `progress_at`，让停滞可被观测。
- 主代理用 `python -m tools.agents.dispatch_wait_protocol wait --status-dir .agent/status`
  一次监视所有在途标记：**任一终态即返回**；`progress_at` 超过 600s 未更新 → `stall`；
  总时长 1800s → `timeout`。禁止再用 `for($i=0;$i -lt 30;$i++){ Start-Sleep 10 }` 式固定 300s 轮询。
- 等待器若被工具时长上限截断，改为后台 job 并用 `job_output --wait` 收取（实测 600s 可用）。
- **禁止**用轮询掩盖子代理真实耗时：每次返回都要报告各子代理已运行时长。
- 方案 B（改 harness 增加子代理完成事件）**冻结**：升级会覆盖改动，且相对方案 A 只多两点收益
  （每次少约 10s 检测延迟、子代理崩溃可见性）。只有实测到"子代理不写任何产物就终止"时再启用，
  且只做"崩溃也写终态文件"这一最小面。
  **→ 2026-10-22 追加：该结论已被 DSH 智能体团队（Team）实测取代，见 §6。原语层不需要改代码，
  Team 自带事件等待与可续跑成员；本节标记文件方案降级为不启用 Team 时的兜底。**

### 2.2 上下文：降斜率 + 强制交接（顾问：决定 2 = partial，已按本地数据修正）

- 采纳：构建/测试/探查输出一律落盘（`.runtime/`、`.agent/logs/`），主会话只读退出码、
  失败摘要与末尾若干行；子代理报告用固定模板 + 长度上限，不贴大段 diff；主代理默认只读
  diffstat，只有触及公共契约、数据模型或安全的文件才读完整 diff。
- 采纳：150k 软提醒 → 完成当前任务后交接；180k → 立即交接、不再派发新子代理。
  交接包除 task_id/改动文件/验证结果/风险/下一步外，**必须**带：已定决策与否决路线（一行一条，
  附 ID）、未关闭的评审意见清单。缺这两项新会话会重开已定问题。
- **反对**（顾问建议，已采纳）：不把"实现→评审→修复→复审"合并成单回合。评审独立性是质量保证，
  合并只是把 token 压力转给子代理。可收窄：复审只核销"修复 diff + 上轮意见逐条"。
- 修正：因为时延与上下文长度几乎无关，**不以"更快"为理由提高交接频率**；交接是为了成本与
  决策一致性。200k 硬闸仍是团队约束。

### 2.3 并行：分阶段放开写通道（顾问：决定 3 = adopted）

阶段 1（立即可用）：任务 N 的**只读评审**与任务 N+1 的**实现**并行——评审不写文件，零写冲突。
阶段 2：从互不共享文件的任务里挑两组，试点 **2 个写通道**（`max_write_channels=2`，默认值）。
阶段 3：试点期零返工、无 `index.lock` 冲突，才允许提到 3（`MAX_WRITE_CHANNELS_CEILING`）。

派发前必须通过 `python -m tools.agents.dispatch_wait_protocol plan --file <plan.json>` 校验，
最小约束集（按风险从高到低）：

1. **写入清单互斥**：每个单元声明 `write_paths`，两两不相交（路径规范化后比较）。
   共享文件要么剥离成主代理串行执行的集成步，要么整块划给一个通道。
   子代理要写清单外的文件 → 写 `blocked` 并停止。
2. **禁止全仓副作用命令**：全仓格式化/自动修复、依赖安装与锁文件更新、代码生成、
   迁移文件生成、`git add/commit/stash/checkout/reset/clean/worktree`。校验器已内置这些规则。
3. **git 串行**：子代理不执行 add/commit。主代理核对 `git status` 的改动是否都在清单内，
   再按路径限定提交。完成判据是标记文件，不是 commit。
4. **测试隔离**：迭代期只跑本任务路径；有写入通道活跃时不跑全量。测试若用固定端口/库/临时目录，
   要么按通道参数化，要么连定向测试也串行。
5. **门禁**：全量测试在工作区静止时对集成后的 commit 执行；失败按任务 commit 二分归因。
   定向测试集 = 改动模块测试 + 直接导入方测试 + 全部契约/安全测试。

## 6. 2026-10-22 追加：DSH 智能体团队（Team）实测与协议修订

顾问在决定 1 里写明的推翻条件之一是"harness 有升级安全的扩展点，使 B 的成本骤降"。当前构建
**已经自带**该能力，且零代码改动，因此本节按顾问给定的推翻条件直接改判，不另开咨询。

### 6.1 实测（本会话内跑的两轮探针，全部可复现）

| 探针 | 做法 | 结果 |
| --- | --- | --- |
| 并行 | `team_task_create` 两条（含 `write_scopes`）→ `spawn_teammate` ×2（`context: fresh`） | 两个成员同时 `running`；各自标记文件写入时间**同一秒**（14:52:27）→ 真并行 |
| 事件等待 | 两个成员在跑时调 `wait_agent(timeout_ms=180000)` | 返回 `{"timedOut":false}`，靠活动唤醒，**不是**轮询；结束后 `list_agents` 显示双双 `inactive` |
| 完成推送 | 直接 `subagent` 一个只回一行的探针，主代理不做任何等待 | 结束消息**自动推入**主代理上下文（`subagent push probe ok …`）→ 轮询在任何情况下都不是必需 |
| 续跑保上下文 | 对已 `inactive` 的成员 `send_message`，要求它不读文件、凭记忆复述上一轮写的内容 | 逐字复述原 JSON，并报告"已执行 2 个 assistant turn" → **成员是持久的，修复轮可续跑同一实现者** |
| 任务板 | `team_task_create` → `claim` → `complete`；`blocked_by` 依赖；`write_scopes` 冲突 | 全流程可用，`claim/complete` 需带 `expected_revision`（CAS）；**`write_scopes` 只给建议**：第二次认领重叠范围时返回 `writeScopeWarnings:["write scopes overlap with task-3"]` 但不阻断 |

### 6.2 协议修订（覆盖 §2.1、§2.3 的默认路径）

1. **多任务批次默认走 Team，不再用 `subagent` + 文件轮询。** 流程：`team_task_create` 建板
   （写 `blocked_by` 依赖与 `write_scopes`）→ `spawn_teammate(context=fresh)` → 主代理**有本地活
   就不等待**（完成消息会随下一轮到达）→ 真正空闲时用 `wait_agent` 单次 300–600s 长等待 →
   唤醒后 `list_agents` + `team_task_list` 对账，追查未回报的成员。
2. **禁止短轮询。** `wait_agent` 是事件订阅，长等待与短等待同样快；实测旧会话 27 次 300s
   shell 轮询、`wait_agent` 返回 `no-active-peer` 的根因是**当时用的是 `subagent` 而不是 team 成员**，
   不是能力缺失。
3. **修复轮续跑同一实现者**：`send_message` 唤醒原成员，保留其上下文与已读证据；
   不再新开"Fix round N"新代理（旧会话每轮新开，等于让修复者从零重读）。
4. **评审角色仍开新的 `fresh` 成员**，不 `fork` 实现者上下文——评审独立性优先于上下文复用。
5. **`write_scopes` 只是建议，不是互斥。** 派发前仍必须过
   `python -m tools.agents.dispatch_wait_protocol plan` 做路径级硬校验；`.agent/status` 标记 +
   等待器降级为兜底（不启用 Team 的单代理环境、或需要跨会话对账时）。
6. **模型与预算**：成员与主代理同模型、各自独立上下文（实测 `cn:deepseek-v4-flash`）；
   `fork` 会把主代理已完成轮次复制给成员，只在确实需要共享推理时使用。

### 6.3 与 §4 收益的关系

并行、事件等待、续跑修复三者叠加，比原方案 A 更进一步：原估计的"关键路径 19,296s → 11,000–12,000s"
来自"只读评审并行 + 2 写通道"；现在修复轮不必从零重读，回合内耗时也应下降。**≤3h 目标不变，
但达成路径改为 Team 化派发 + 门禁分级。**

## 7. 2026-10-22 端到端验收（真实批次，非单测）

用与生产同形的 3 单元批次跑完整流程：2 个并行写单元 + 1 个只读评审 + 2 个由评审意见驱动的修复轮。

| 阶段 | 做法 | 实测 |
| --- | --- | --- |
| 派发前校验 | `plan --file .runtime/protocol-e2e-plan.json` | `ok=true`、`write_channels=2`、`read_only_units=1`、`forbidden_commands=[]`，exit 0 |
| 并行派发 | `spawn_teammate(fresh)` ×2，各自先写 `running` 标记再动工 | 两单元同一时刻起跑，21s 内双双 `done`，各 3 测试通过 |
| 事件等待 | 同一时间起一个**兜底等待器**后台 job 监视 `.runtime/agent-status` | 20.0s 返回 `action=return`，两个终态标记齐备，exit 0；全程零 shell 轮询 |

| 修复轮 | `send_message` 唤醒原实现者（不新开成员） | 各加 1 条测试，4+4 通过；标记 `started_at` 保留首轮值（1792668030/36），`finished_at` 更新为 1792668133/135 → 同一成员续跑 |
| 独立复核 | 主代理自己跑 `pytest` 与 `git status` | 8 passed；无任何被跟踪文件被改动（工作全在 `.runtime/`） |

**批次墙钟：19:20:30 首次派发 → 19:22:15 两个修复轮落地，共约 105 秒**（含评审与两轮修复）。
旧协议下同形批次是"3 个串行回合 × 约 420s + 每回合 1–3 次 300s 轮询"，量级 15 分钟以上。

### 7.1 测试中发现并修掉的三个真实缺陷

1. **BOM 标记被静默跳过**：PowerShell `Set-Content -Encoding UTF8` 写的标记带 BOM，
   `json.loads` 抛错被 `except` 吞掉 → 标记"不存在" → 等待器空转。已改为 `utf-8-sig` 读取。
2. **空标记目录无限自旋**：`no-marks` 不在返回集合里 → 死循环。已加
   `no_marks_grace_seconds`（默认 60s）宽限窗，并单独覆盖两种情形（宽限内到达 / 宽限后放弃）。
3. **定向 pytest 被误判为全量门禁**：原正则 `pytest\b(?![^\n]*\.py)` 会把
   `pytest .runtime/protocol-e2e/a -q` 判成跑全量。已改为"无 `.py` / 无 `::` / 无嵌套目录路径才算全量"，
   并补 2 条测试（`pytest tests`、裸 `pytest` 仍拦截）。

协议测试合计 **19 passed**；`flake8` 0 告警。

### 7.2 仍未验证

- 长时间真实任务（>10 分钟/单元）下的 `stall` 与 `hard_limit` 路径只用单测覆盖，未在真实批次触发。

## 8. 顾问调用在批次中的位置（2026-10-22 补）

§1–§7 只覆盖**执行层**：派发、等待、并行、门禁。顾问属于**决策层**，不在派发链路上——
它不参与等待、不影响并行、也不该出现在每个批次里。§7 的端到端验收**没有**顾问调用，
那是正确的：该批次是机械实现 + 有界评审，没有架构取舍可咨询。

### 8.1 触发点（对应 `expert-advisor` SKILL.md 场景表）

| 批次阶段 | 何时咨询 | 典型场景 |
| --- | --- | --- |
| 范围确定后、写 `plan` 前 | 非琐碎的架构/接口/数据流/实施顺序判断 | 行 11 定案前方案；待办 ≥5 且含契约变更时顺带问"哪些可砍" |
| 派发前 | **不咨询**，这是机械动作 | — |
| 成员实现中 | **不咨询**；成员（worker）禁止调用顾问 | SKILL.md 明确只允许 lead 发起 |
| 评审返回后、修复前 | 评审给出两条以上修复路线，或根因候选互斥 | 行 7 修复路径选择；行 8 排查僵局 |
| 门禁/打包前 | 实施后复核：删改调用、原地更新、并发、跨口径映射 | 行 1、行 3、行 6 |
| 高影响故障两轮后 | 证据相互矛盾、无法用现有观测区分 | 行 8；静默丢数据用 data-loss 档 |

**时机要求**：顾问 live 调用一律用后台 job 启动，与成员运行重叠；它耗时 45–215s，
绝不允许成为关键路径（旧会话 4 次 live 合计 471s = 墙钟 1.9%，就是这么做到的）。

### 10.3 记账与净收益判定

每次顾问调用在账本之外补三个数：`hidden_wait_s`（顾问实际耗时）、`coord_s`（等待期并行产生的
额外协调，含成员被中途打断、上下文重建）、`discarded_s`（结论推翻后废弃的工作量）。

**净收益 = hidden_wait_s − (coord_s + discarded_s)**。连续 3 次净收益 ≤ 0 即撤销本节，回到阻塞等待。
不允许只记 hidden_wait 就宣称"已并行化"。

首笔记账（2026-10-23，run `94ca423f`）：`hidden_wait_s` 65、`coord_s` 0、`discarded_s` 0 →
净收益 **+65s**。等待期完成的是"E2E 切片固定开销拆解"，即 §10.6 那张表的来源；它不依赖顾问结论，
所以即使顾问三项全部推翻也不会作废——这是本规则的合格样本。

### 10.4 反例与推翻条件

最强反例：顾问改写的是需求本身——连"需求已稳定的骨架"也会报废，`discarded_s` 会超过
`hidden_wait_s`。另两个推翻条件：并行任务争抢资源导致顾问耗时上升 >20%；并行任务本身需要
按结论返工（`coord_s` 计入后转负）。

### 10.6 副产品：单元时长与有效并行度的关系

| --- | --- | --- |
